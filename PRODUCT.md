# MailSchema

## Register

brand

## Users

Agent builders, email service developers and specification implementers assessing a shared way to describe and complete actions offered through email. Readers move between a concise explanation, precise draft semantics and a concrete working example. People reviewing content retain a normal usable path.

## Product Purpose

MailSchema is building an open standard for agents to work with services through email. Mail Action Protocol (MAP) defines the common message and processing rules. Type contracts define particular interactions, and the Registry publishes their versions, examples, maintainers and service support. A support record names the exact contract and binding. A client uses an independently enabled service connection and the service's own permission checks.

The browser contribution path validates and previews contracts and service records using the repository's parsers, then hands the checked file to GitHub for review. Git remains the only source of accepted Registry state. MailSchema does not maintain a second submission queue or contributor account system. Language packages remain maintained implementation surfaces and release when their APIs or bundled artifacts change.

The initial contracts describe campaign send approval, publication approval, address confirmation and account security responses. Real service integrations and independently operated implementations remain separate evidence milestones. Sourcey renders the specification and is not counted as an action service. The site must explain the practical opportunity and invite participation without implying independent adoption or IETF status.

## Brand Personality

Precise, assured, luminous. The selected yellow-and-blue Direction 03 identity gives the Astro specification site a strong infrastructure character, legible technical detail and restrained movement.

The language explains familiar work and why a common standard is useful. Use ordinary sentences and concrete examples. Avoid generic future-facing slogans and a homepage dominated by implementation criteria or technical punchlines. Review proposed language before applying another site-wide rewrite.

## Anti-references

Earlier A-Mail identity explorations and unselected MailSchema concepts are historical, not visual references. Avoid invented adoption badges, fake partners, generic SaaS feature grids, decorative terminal dashboards, excessive safety messaging and product copy that exposes implementation bookkeeping.

## Design Principles

- Lead with agents; make human control concrete through behavior.
- One coherent family: MailSchema, MAP, Types, Registry.
- Organise the Registry around submitted types. Record product support and evidence within the applicable type and version.
- Develop a useful collection with clear maturity labels and reuse of existing standards. Proposed additions require a definition and examples before being presented as usable types.
- Teach through a concrete exact-terms decision.
- Distinguish the working draft and planned implementation evidence honestly.
- Respect existing standards and existing service authorization.
- Give long-form reading as much attention as the homepage.

## Accessibility & Inclusion

Readable at mobile and desktop widths, keyboard access, visible focus, semantic structure, clear contrast and reduced-motion support. Information must remain understandable without color or JavaScript. Interactive examples progressively enhance static explanations.
