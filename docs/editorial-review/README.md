# MailSchema language and type collection review

Status: accepted and applied on 23 September 2026. This packet preserves the copy and collection assessment. It is not a deployment record.

## Agreed direction

MailSchema is building an open standard for agents to work with services through email. A service describes an interaction that different agents and inboxes can understand. People can continue to participate through readable email and the service's normal interface.

The Registry centres on submitted type definitions. Implementing products may be listed against a type and version, with evidence of support. A product listing alone is not a registry entry.

This replaces the earlier implementation-directory model in the site and architecture notes. The names MailSchema, Mail Action Protocol (MAP), Types and Registry remain in use.

## Editorial decisions

- Explain the work an agent can participate in before introducing protocol concepts.
- Use ordinary sentences. Headings should introduce the subject without becoming a sequence of slogans.
- Keep requests, review decisions, edits and later sending operations distinct where the distinction matters.
- Use permission, result and version consistently. Avoid replacing them with authority, outcome and revision merely for variety. A content revision and a type version are different things.
- State working-draft status once in the overview and where a reader needs it to judge a specific example.
- Separate a type definition's maturity from a product's implementation evidence.
- Use existing standards where they cover the interaction. An external standard's maturity does not establish the maturity of a proposed MAP binding.
- Avoid unearned claims about supported clients, adoption, conformance, safety or IETF status.

## Application and remaining specification work

The homepage, six specification chapters and supporting pages now use this language. The five-entry Registry contains one semantic draft, two proposals and two reuse assessments. Adding these records does not establish new implemented MAP types. The collection document identifies what exists today, what needs a new definition and where a binding to existing work may suffice.

Navigation, search, type routes, the proposal template and architecture notes were updated together. The route plan is in [Types and Registry](type-registry.md#site-structure). The local preview is updated; no deployment has been made.
