# Standards references

MAP uses existing standards for email, authentication, data representation and HTTP. The following references identify their role and the additional requirements MAP imposes. The Internet-Draft lists the normative dependencies.

The [Structured Email working group's charter](https://datatracker.ietf.org/group/sml/about/) covers the message container and trust guidance but leaves recipient use of extracted data and domain-specific vocabularies outside its current scope. MAP's decisions therefore need their own specification and venue; using the SML container does not make MAP an SML working-group item.

## Service interfaces and discovery

The [research catalogue](/interfaces) records the wider comparison, primary sources, publication status and design assessment for each interface. It distinguishes execution protocols, descriptions, delivery, identity and established workflows. Research coverage is not a claim of MAP interoperability.

- [OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html) describes the illustrative native HTTP API.
- [Arazzo 1.1.0](https://spec.openapis.org/arazzo/v1.1.0.html), [AsyncAPI 3.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0) and [WoT Thing Description 1.1](https://www.w3.org/TR/wot-thing-description11/) are prior art for reusable binding descriptions. No new general mapping language is specified here.
- [OAuth Protected Resource Metadata, RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html) can support explicit setup for an independently selected resource.
- [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) supply the native calls and structured results used in the illustrative walkthrough. [MCP Tasks](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) is a separately negotiated extension. Neither is a normative MAP MCP binding.
- The proposed [Agent Communication Protocols charter, revision 00-04](https://datatracker.ietf.org/doc/charter-ietf-agentproto/00-04/) addresses correlation and lifecycle of agentic dialogs across protocols. It explicitly excludes agent decision-making semantics and client UX. MAP defines the meaning and authorization conditions of a service action described in email, not dialog-context propagation. A future binding can carry any relevant dialog context without making it a MAP requirement.
- The proposed [Discovery of Agents With Names charter, revision 00-08](https://datatracker.ietf.org/doc/charter-ietf-dawn/00-08/) addresses initial discovery of public AI-resource properties. It excludes capability catalogues, subsequent communication and identity management in its initial scope. MAP's configured type and service catalogues do not become a global agent-discovery system. Both charters are proposals as of 4 October 2026, not adopted specifications or assigned venues for MAP.
